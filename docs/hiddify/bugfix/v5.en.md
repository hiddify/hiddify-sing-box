names the commit that fixes it.

## Keep top left working proxies at rest for as long as the kept ones answered

Commit: `52c7d3335`

**What happened:** with a profile of 541 REALITY links, keep top used the 5 fastest and the other
136 that answered rested, with the pings of the pick, for as long as those 5 answered. The ones at
rest were looked at again only when a kept one died, and then in the order of their last pings,
the ones that failed last: a proxy that failed once (two lost tests in a row in a filtered
network) was not tested again for 24 hours with `quick`, however well it worked since. A
subscription's update added new proxies, never tested, and they rested untested too. A proxy at
rest that the user tested by hand, and that answered faster than the kept ones, stayed at rest
unless a place was free. Users saw the same proxies asleep after every update, and proxies that
worked in other clients for days marked as failed.

**Fix:** keep top has a `refresh` option (1 hour by default; hiddify-core sets 1 hour). With every
place taken, a pick goes through the ones at rest every `refresh`: the kept ones that answer stay
untested, and a faster one takes the place of the slowest. In such a pick an answer older than
`refresh`, also of a proxy that failed since, counts as none, so it is tested again; a proxy that
never answered still waits 24 hours. A reload that brings proxies never tested starts this pick at
once. A proxy at rest that answers a test faster than the slowest kept one takes its place. Tests:
`TestH_KeepTopRefreshLooksAtTheOnesAtRest`, `TestH_KeepTopReloadTestsTheNewOnes`,
`TestH_KeepTopFasterAtRestTakesThePlace`, `TestH_KeepTopTopPingHint`.

## WARP behind a detour started before its detour could carry traffic

Commit: `0e268032f`

**What happened:** WARP in WARP logged `WARP auto mode: no tunnel answered, using wireguard (score 0)`
on its first start, and sometimes restarted 20 seconds later. The outer WARP starts together with
the inner one, which is still registering its devices or choosing its tunnel for several seconds,
and every dial through it fails at once (`WARP is not connected yet`). So the outer one named its
network by the interface type alone, and rated its tunnels and scored its endpoints under that
name. Its race got no answer, so it drew a tunnel without one. Its scanner found nothing, and
`confirmAuto` then blamed the tunnel for not connecting. The earlier fix, `7163b2c41`, only waited
before the race. It was capped at 30 seconds, which a slow registration (33 seconds seen) used up.
It did not wait for the member of a group detour (a group is always ready itself) or for a lazy
detour at rest (it says it is ready).

**Fix:** once WARP has its devices, it waits for its detour before it names the network, races,
scans or connects, in every mode (`protocol/warp/h_detour_wait.go`). For a group it follows the
member in use (`adapter.GroupPath`, now shared with the DNS group and the monitoring). It holds a
lazy detour while it waits. It waits with no limit while the detour registers or searches, and
for up to 30 seconds while it connects. `confirmAuto` and the port rotation no longer blame a
tunnel or a port while the detour is down. Tests: `TestH_WARPStartWaitsForItsDetour`,
`TestH_WARPStartWaitsForTheMemberOfAGroupDetour`, `TestH_WARPStartHoldsALazyDetour`,
`TestH_WARPWaitsForAWarmingDetourWithoutALimit`, `TestH_WARPStartDoesNotWaitForAFailedDetour`,
`TestH_WARPDetourReady`.

## Psiphon never connected on Windows

Commit: `996a3e456`

**What happened:** since the desktop core runs in a process of its own, Psiphon outbounds on Windows
kept logging `psiphon.SetNoticeWriter: notice writer already set, starting again in ...` and never
connected (hiddify/hiddify-app#2630). tunnel-core accepts a notice writer only while the writer is
the default, which it finds by comparing with `os.Stderr` at the time of the call. The Windows core
points `os.Stderr` at NUL once it is set up (`hprocess.DetachStdio`), so the notice hub was never at
the default, and the failure stayed for the life of the process.

**Fix:** the hub resets the writer to the default before its one install
(`protocol/psiphon/psiphon.go`). Nothing else in the process sets a notice writer. Test:
`TestH_NoticeHubInstallsWhenStderrIsReplaced`.

## Shadowsocks: cipher names that Xray accepts were rejected

Commit: `7b27ba2ee`

**What happened:** Xray accepts several names for the same Shadowsocks cipher, for example
`chacha20-poly1305` and `aead_chacha20_poly1305` for `chacha20-ietf-poly1305`. Subscriptions written
for Xray clients use those names, and sing-box refused the outbound:
`initialize outbound/shadowsocks[...]: unknown method: chacha20-poly1305` (hiddify/hiddify-app#2622).

**Fix:** the Shadowsocks inbound and outbound map the Xray names to the sing-box names before
creating the cipher (`protocol/shadowsocks/h_method.go`): `aead_aes_128_gcm`, `aead_aes_256_gcm`,
`chacha20-poly1305`, `aead_chacha20_poly1305`, `xchacha20-poly1305`, `aead_xchacha20_poly1305` and
`plain`, in any letter case. They are the same ciphers on the wire. Test:
`TestH_ShadowsocksXrayMethodNames`.

## Windows: the tunnel did not start when another adapter held its address

Commit: `fe80f09` in `replace/sing-tun`

**What happened:** Windows refuses to give an interface an address that another interface already
holds. sing-tun cleared the addresses of its own adapter only, so when another adapter held
`172.19.0.1` (one left disconnected by an earlier run or by another VPN, or a second tunnel still
up), the tunnel did not start: `set ipv4 address: The object already exists`
(hiddify/hiddify-app#2619). With a `tun0` already there, the new adapter is named `tun1` and sits
beside the old one and its address.

**Fix:** on that error the tunnel looks for the interfaces that hold its addresses. An interface
that is not up keeps the address for nothing, so the address is taken off it and set again, as
WireGuard for Windows does. An interface that is up is in use and is left alone; the error names
it. Test: `TestH_ConflictingAddresses`.

## WARP scanner: endpoints lost points they did not deserve

Commit: `afbfb83f1`

**What happened:** the scanner took a point from every endpoint that did not answer a probe. When
no endpoint answered at all (the network was down, or the noise did not get through), the
endpoints that worked lost a point at every such scan, and the failover marked the endpoint in
use down before it knew whether any other answered. Every random address that failed was also
saved with -1: the ranges hold millions of address and port pairs, so such an address is all but
never drawn again, and these records pushed the endpoints that work out of the 64 a network kept.

**Fix:** the failures of a scan count only when some endpoint answered in it, and the endpoint in
use (WARP failover, MASQUE scanner) loses its point only once another one answers. Only an
endpoint that answered on the network before is marked down; records of endpoints that never
answered are dropped when the scores are read, and a network keeps up to 128 endpoints. Tests:
`TestH_ScanWithoutAnswerKeepsScores`, `TestH_BookDropsNeverAnswered`, `TestH_ScanUsesScores`.

## WARP: an incomplete profile in the config stopped the whole config

Commit: `ec647f4b7`

**What happened:** a `warp` endpoint can carry its own WireGuard profile (`private_key`,
`interface`, `peers`). Since `e10461336`, a profile that cannot run a tunnel (no peer, no peer
public key, no tunnel address, no peer address and port) made the config fail to load. The app
builds this profile from a WireGuard config to WARP, with what that config has. So one such
entry, for example a link without a tunnel address, stopped every connection of the config.

**Fix:** an incomplete profile is not an error any more. The endpoint logs a warning that says
what is missing, does not use the profile, and goes on as a `warp` endpoint without a profile
does: it takes a saved device from the pool, or registers a new one. A profile with peers or
addresses but no private key, which was ignored silently, gets the same warning. A device the
API returns incomplete still fails the start, and a saved device that is incomplete is still
retired. Test: `TestH_WARPIncompleteProfileIsNotUsed`.

## Balancer: one added by a hot reload never followed the URL tests

Commit: `e50bc7749`

**What happened:** when a config change added a balancer under a new tag and the core applied it
without a restart (hot reload), the balancer started before the monitoring knew its group. Its
subscription to the group's test results failed, and the part of the balancer that follows them
ended at once. The balancer stayed on the member it had started on: it did not move to a faster
member, and did not leave a member that had stopped working, until the core restarted.

**Fix:** a subscription to a group the monitoring does not know yet is kept, and the group gets
it when the monitoring registers it. Test: `TestH_SubscribeBeforeTheGroupIsRegistered`.

## AmneziaWG, WARP: every check of a config left a network stack behind

Commits: `5ba8c1961`, `ab34471a2`

**What happened:** an AmneziaWG endpoint, and WARP in AmneziaWG mode, made its tunnel (a
user-space network stack) when the endpoint was created, not when it started. Only an endpoint
that started is closed. The app checks a config before every start and every hot reload by
building it and dropping it without starting it, so each check left one network stack in memory
for every such endpoint, for as long as the core ran. Next to it: closing the system tunnel of an
AmneziaWG endpoint twice, or the device of a MASQUE tunnel twice, crashed the core, and the
system tunnel's interface was never closed.

**Fix:** the AmneziaWG device makes its tunnel when it starts. The system tunnel and the MASQUE
device close once, and the system tunnel closes its interface. A packet the MASQUE stack sends
after the close gives its buffer back. Tests: `TestH_DeviceMakesItsTunnelAtStart`,
`TestH_SystemTunClosesOnce`, `TestH_StackDeviceClose`.

## Tunnel server: a full queue could stop the whole server

Commit: `ed7a5b14a`

**What happened:** the tunnel server keeps up to ten waiting connections for each client. When a
new one came in and the queue was full, the server took out the oldest to make room, and waited
for it. If connections through the tunnel had used up the queue in that instant, there was
nothing to take: the server waited for good, holding its lock. After that no client could
register a connection and no connection through the server went out, until a restart.

**Fix:** making room never waits: the new connection goes in, or the oldest is taken and it is
tried again. Test: `TestH_ServerQueueFullWhileDialsDrainIt`, which stopped after about a hundred
connections before.

## XHTTP server: an IPv6 host without a port was answered 404

Commit: `649d3e1c5`

**What happened:** an XHTTP inbound with `host` set to an IPv6 address refused its own clients.
For such a host on the default port a client sends `Host: [2001:db8::1]`, the address in brackets
with no port. The server split every Host with a colon as host:port, which this is not, so
nothing matched and each request got 404.

**Fix:** the server compares the host alone: lower case, without the port and without the
brackets, on both sides. Test: `TestH_ServerHostMatchesBracketedIPv6`.

## XHTTP: a server with a small sc_max_each_post_bytes refused every upload

Commit: `01053ace8`

**What happened:** the earlier fix for `sc_max_each_post_bytes` of 8192 bytes or less
(`af9c20a75`, which stopped a crash) raised such a value to 8193. A server that sets the value
refuses a bigger upload with status 413, so connections to it (`4096-4096`, `1536-6144` in
subscriptions) connected and then failed at the first full upload. Separately, over HTTP/1.1 an
upload request that could not be written crashed the app instead of failing the upload.

**Fix:** the client keeps to the value: uploads are cut to it, down to a single byte. A request
that cannot be written is an error of that upload. Tests:
`TestH_XHTTPHonoursASmallScMaxEachPostBytes`, `TestH_UploadWriterPiecesFitThePost`,
`TestH_XHTTPPostPacketWriteErrorIsAnError`.

## VLESS: a dial that failed after connecting left the connection open

Commits: `847e691dc`, `dad752075`

**What happened:** a VLESS dial that failed after the connection to the server was made did not
always close it: with `flow` `xtls-rprx-vision` and no TLS, REALITY or VLESS encryption (every
dial of such an outbound), with `packet_encoding` `packetaddr` and a domain destination, and
with an unknown network. The connection stayed open and was kept until the core stopped. The
earlier fix (`ea3c70fa5`) covered only the failed handshakes.

**Fix:** a dial that returns an error closes its connection, whatever failed. A VLESS outbound
with a Vision flow and no TLS, REALITY or VLESS encryption is refused when it is created, with
"flow xtls-rprx-vision needs TLS, REALITY or VLESS encryption". Tests:
`TestH_VLESSFailureAfterConnectClosesConn`, `TestH_VLESSVisionNeedsALayer`.

## WARP: an incomplete device was saved and tried at every start

Commit: `e10461336`

**What happened:** a WARP device config without a peer, a tunnel address or a key cannot run a
tunnel. It was only noticed by the code that builds the tunnel, on every try. When the WARP API
answered a registration with an incomplete device, that device was saved to the pool and handed
out again at each start, and the endpoint retried "start WARP endpoint" for good, shown as
searching. The same held for an incomplete profile written in the config.

**Fix:** a device is checked where it comes in. An incomplete profile in the config failed the
config when it loaded, with what is missing (changed in `ec647f4b7`: it is now left out with a
warning, and the config loads). A device the API returned incomplete ends the start as failed,
with the reason, and is not saved. A saved device that is incomplete is retired when the pool
hands out devices. Tests: `TestH_WARPIncompleteRegisteredDeviceFails`,
`TestH_WARPIncompleteSavedDeviceIsRetired`.

## WARP: a restart ran next to the start it replaced

Commit: `7232bd18e`

**What happened:** when WARP starts again (auto mode leaves a tunnel that did not connect within
20 seconds, a device is retired, the detour moves), the start it replaces was only marked as
ended. It went on for as long as its endpoint scan took, next to the new start: both registered,
scanned and dialed with the same key. And it could still publish what it had made: an inner
tunnel installed after the restart had removed the old one stayed open beside the new start's, a
second device with the same key that nothing closed, or its scanner state replaced the new
start's. The earlier fixes (`00f7b6e63`, `8db9e7ba2`) only stopped the crash this caused.

**Fix:** each start is a session with its own context: when it ends, its scans and probes stop. A
session ends under the endpoint's lock, and the inner tunnel, the scanner state, the device and
the chosen tunnel are set only while their session is the current one. A new start waits until
the one it replaces has returned. The scanner's checks work for their own session, and a
replacement that did not happen because the start ended is no longer recorded as a switch. Tests:
`TestH_WARPEndedStartPublishesNothing`, `TestH_WARPStartWaitsForTheOneItReplaces`,
`TestH_WARPScanEndsWithItsStart`.

## AmneziaWG: a connection that ended by itself was never made again

Commit: `a30f1692d`

**What happened:** the AmneziaWG endpoint (and WARP in AmneziaWG mode) connected again only when
the network interface changed. When its connection to the peer ended for another reason (a
detour whose stream ended, a proxy that restarted, the connections being closed without a new
interface) the device stopped receiving and went on sending into the dead connection: no traffic
until the next interface change or a restart. A reconnect could also fail for good when closing
the old connection reported an error of the detour's own.

**Fix:** the bind dials its connection again a second after it ended, by itself, and reports a
path change, as the WireGuard endpoint does. An error from closing a connection is logged and no
longer keeps the bind closed. Tests: `TestH_BindReconnectsByItself`,
`TestH_BindCloseErrorDoesNotKeepItClosed`.

## WireGuard, AmneziaWG, WARP: a stalled detour froze the tunnel and could still hang the disconnect

Commits: `82996a60b`, `373cb64d2`, `ffc750e6b`

**What happened:** with a WireGuard, AmneziaWG or WARP endpoint behind another proxy (a
`detour`), the device sends its packets with its own locks held, and the bind wrote to the detour,
and dialed it, inside that send. A proxy that carries UDP in a stream (VMess, VLESS, Trojan,
anything multiplexed) blocks the write while its stream is stalled, and a proxy that does not
answer blocks the dial. One packet then held the whole device: no status, no move to a fallback
address, no reconnect after a network change. The earlier fixes (`96652cba6`, `41c3193aa`) made
the close cut the detour's connections first, but with a fallback address, which hiddify-core
gives every WARP behind a detour, the close waited behind the fallback's move before it got that
far, and a reconnect that was waiting could open the bind again behind the close: disconnecting
or stopping the core still hung.

**Fix:**
- A connection through a detour that is not a plain UDP socket is written from a queue by a
  goroutine of its own; a full queue drops the packet, as a socket does. A UDP socket is written
  directly, as before.
- AmneziaWG dials its connection in the receive loop, with no lock held, and keeps the packets
  sent meanwhile (up to 16, for 5 seconds) for the connection being made. WireGuard runs one dial
  at a time outside its lock. A dial that ends after the bind was closed or opened again is
  thrown away.
- Closing the endpoint closes the bind first and for good: it does not open again.
- The fallback's Close no longer waits for a move.

Tests: `TestH_CloseDoesNotWaitForAMove`, `TestH_StalledSendDoesNotHoldTheDevice`,
`TestH_StalledDialDoesNotHoldTheDevice`, `TestH_DeviceCloseWithStalledDetourAndFallback`,
`TestH_StalledSendDoesNotHoldTheEndpoint`, `TestH_ClientBindCloseDuringASilentDial`,
`TestH_EndpointCloseWithStalledDetourAndFallback`.

## Call tunnel: a waiting server started a new call session every two minutes, and late clients went past the router

Commit: `4bb68ea76`

**What happened:** the server side (the `call` inbound) started its call session and then waited
60 seconds for a first client. With no client yet, the connect failed and, since the inbound
retries, started again: a server nobody had joined made one more call session about every two
minutes. On VK the sessions left behind could not be stopped at all. A client that joined one of
them later was served by a bridge that had never been given the inbound's handlers, and such a
bridge opened each destination itself, so the connection skipped the router and its route rules.
The first messages of any bridge could do the same, as the handlers were set a moment after the
bridge was made. And closing the inbound or the outbound did not leave the call: the session and
its rejoining loop ran until the process ended.

**Fix:** the server side is connected once it has joined the call, and waits there for the
client; nothing times out while it waits. The handlers are part of the call's configuration and
every bridge has them from the moment it is made; a server-side bridge no longer dials at all, and
refuses a connection it has no handler for. Closing the inbound or the outbound leaves the call
(VK, Telemost, Dion, WB Stream, Bitrix24), also when the box closes while it is still connecting.
Tests: `TestH_CreatorBridgeHasItsHandlersFromTheStart`,
`TestH_EveryPeerBridgeHasTheSessionsHandlers`, `TestH_ClosedBridgeStopsJoining`,
`TestH_BridgeCloseLeavesTheCall`, `TestH_ConnectWithRetryClosesALateBridge`.

## Monitoring: a URL test group could start the closed monitor again

Commit: `df38cab6e`

**What happened:** a URL test group wakes the monitoring on every connection, and that starts its
scheduler when it is not running. Closing the monitoring stopped the scheduler first and ended the
rest later, so a connection in between started the scheduler again for a closed monitor, which
could also panic the core while it closed.

**Fix:** closing marks the monitoring closed before it stops anything, and a wake starts nothing
after that. Test: `TestH_TouchAfterCloseStartsNothing`.

## Monitoring: an outbound removed during a test cycle stopped the periodic tests

Commit: `c97459355`

**What happened:** a test cycle waits for one result per outbound it queued. An outbound that a
hot reload removed while its test waited in the queue gave no result, and neither did a retry of an
outbound that was not ready when the retry could not be queued again. The cycle then waited for
good: no periodic test ran again for the rest of the run, so pings went stale and lowest-delay
stopped following them, and a balancer held its members as during a cycle.

**Fix:** every queued test ends with a result: its own, a timeout, or, when it is not run, a failed
one that records nothing for the outbound. Test: `TestH_CycleEndsWhenAQueuedOutboundIsRemoved`.

## Psiphon: closing could hang the core, and a closed outbound started again

Commit: `08f9ffaa4`

**What happened:** the notice hub that passes Psiphon's notices to every instance (`df13d433d`)
was removed when the last instance stopped listening, under the hub's lock, with a call that takes
Psiphon's own notice lock. Psiphon holds that lock while it writes a notice, and the hub takes its
lock for each notice. Closing the last Psiphon stops its controller, which writes notices as it
stops, and then stops listening: when the two met, closing the core hung for good (a disconnect or
a profile change that never finished). Also, the loop that starts the controller again (`3c5e93945`)
ran until the core stopped, not until the outbound closed: an outbound closed by a hot reload or a
lazy unload started its controller again five seconds later.

**Fix:** the hub is installed once for the process, outside its lock, and never removed; with no
instance listening a notice goes nowhere. The outbound has its own context: closing it ends the
loop and waits for it, and the data store is closed only once the controller stopped. Tests:
`TestH_NoticeHubCloseWhileNoticesAreWritten`, `TestH_ClosedOutboundStopsRunning`.

## Call (Telemost): a relay that could not be made still crashed the app

Commit: `9ca18bc2c`

**What happened:** the fix of a Telemost relay failure (`e727940f5`) replaced the exit with a log
line, but the call session went on without a relay, or with the previous one, already closed. The
next signalling message of the session (the answer to the publisher's offer, the subscriber's
offer, an ICE candidate, a screenshare change) called into it, and the app still crashed, one
message later. A creator connect that timed out also left its call session running and joining
again for the rest of the process.

**Fix:** the relay belongs to one session of the call's websocket: it is made when the session
starts and closed when it ends. When it cannot be made, the session ends and the bridge joins
again, as after a dropped session. A closed relay answers with an error, and signalling that comes
with no relay is refused. A connect that gives up closes the session it started. Tests:
`TestH_ClosedRelayAnswersAnError`, `TestH_SignallingWithoutARelayIsRefused`,
`TestH_ClosedBridgeStopsJoining`.

## XHTTP: with c_max_reuse_times a connection got a closed client

Commit: `ddee94644`

**What happened:** since the XHTTP clients are closed when they are not needed (`511c5cf72`), a
client taken out of the manager is closed as soon as nothing runs on it. A connection picked a
client for its upload and another for its download, and counted them as running only after both
picks; without a `download` block both came from the same manager. When the first pick used up the
client's `c_max_reuse_times`, the second took it out with nothing running on it and closed it, so
the connection went out on a closed client. With `c_max_reuse_times` 1 every connection failed;
with a range such as 64-128, as many share links have, one connection per client did. Also, closing
a client marked it with the flag a failed request sets, which only means "do not use it again":
on a client that several connections share, one failed request then closed every connection the
client dialled after it.

**Fix:** a pick counts the client as running under the manager's lock, and without a `download`
block the download uses the upload's client, as in Xray. Closing a client has its own flag. Tests:
`TestH_XmuxPickedClientIsNotClosedByTheNextPick`, `TestH_XmuxReuseOnceRoundTrip`,
`TestH_FailedRequestDoesNotCloseLaterConnections`.

## Network change: DNS servers and HTTP clients were not reset

Commit: `e40e3cbb6`

**What happened:** on a network change (Wi-Fi to mobile, a wake on Windows, the reset the app asks
for) the network manager closes the connections and tells every endpoint, inbound and outbound,
and then has the router reset the rest: the HTTP clients, the DNS servers and the process cache.
An earlier commit (`d3e622b45`) removed that last call to stop a recursion that the committed code
never had, and nothing else called it. DNS servers kept the connections of the old network until
they failed by themselves, and a DNS group kept the scores and the chosen server of the old
network, although the DNS group fix (`900d60c40`) says they are "forgotten when the network
changes".

**Fix:** the network reset ends with the router's reset again, as in upstream sing-box. Nothing the
router resets calls back into the network manager. Test: `TestH_NetworkResetReachesTheDNSServers`.

## Keep top: a proxy taken out of rest for its answer showed no ping

Commit: `6ae8c47db`

**What happened:** with keep top, a proxy at rest that answered a test asked for by its tag (the
app tests the list) is used at once (`keepTopBackLocked`). keep top does that while the test's
result is being recorded, before the test has ended, and `setActive` marked that answer of a moment
ago as a cached result and asked for a new test. The new test found the old one still running,
joined it and took its result as it was, still marked cached; nothing replaced it until the next
cycle. The app showed the proxy with no ping until the user tapped it (hiddify-app#2608, Android,
the "working" keep top mode).

**Fix:** an outbound taken out of rest whose result is of this run, worked, and is younger than
`recentResult` keeps it as it is; only an older or cached result counts as cached until the new
test is in. Test: `TestH_FreshResultStaysWhenTakenOutOfRest`.

## MasterDNS: with resolvers "auto" the tunnel never opened

Commit: `a9e759daf` (MasterDnsVPN fork `2f38bf9`)

**What happened:** with `smart_pool`, a resolver joined the pool once it answered a plain query
for `pretest_domain`. Many public resolvers, most of the `auto` list in filtered networks, answer
ordinary names but drop or rewrite the long TXT queries of a tunnel domain. The pool filled with
them, the client's MTU test through the pool failed (`reason=UPLOAD_MTU | value=0`, then "No
valid connections found after MTU testing"), and every connection ended with `tunnel not ready
after 30s: N of M resolvers answered the probe, no session with the server yet`.

**Fix:** after the plain query, each resolver is sent the client's smallest upload and download
MTU probes for the tunnel domain, through the same DNS transport (UDP, TCP, DoT or DoH), and joins
the pool only when the server's answers come back intact, as the DNSTT outbound already tests a
resolver with a real tunnel. The MasterDnsVPN library builds the probes (`TunnelProbes`), and
`dnspool.Exchange` sends them.

## XHTTP: a stream the server refused showed only "read/write on closed pipe"

Commit: `fc0a99b5b`

**What happened:** when the server answered the XHTTP download request (stream-down or
stream-up mode) with a status other than 200, for example because the path, host or padding did
not match its settings, the client closed the stream without saying why. Every read then failed
with `io: read/write on closed pipe`, and the log gave no hint of the server's answer.

**Fix:** the stream keeps the server's status, and reads return `bad status code: <status>`, as
uploads already did.

## Windows: VPN mode did not start when IPv6 was turned off

Commit: `1ac827bdb` (sing-tun fork `0d36e4b`)

**What happened:** with IPv6 turned off in Windows (the `DisabledComponents` registry value, or the
IPv6 binding removed from the adapters), the TUN adapter has no IPv6 interface, and setting its
IPv6 address failed with "Element not found". The TUN inbound returned `configure tun interface:
set ipv6 address: Element not found.` and VPN mode did not start at all.

**Fix:** sing-tun asks for the adapter's IPv6 interface first. When Windows has none, it logs a
warning and runs the tunnel on IPv4 alone: no IPv6 address, route or interface option is set, and
strict route blocks IPv6 as it does for an IPv4-only tunnel. The TUN inbound leaves the IPv6
address out of the stack too, so the system stack does not listen on an address the interface
never got.

## Userspace stack: a connection the app closed went on taking data at full speed

Commit: `e21fa6255` (sing-tun fork `73b1d97`)

**What happened:** the userspace TCP stack, which every WireGuard endpoint runs its connections
on, closed a connection with nothing left to read by sending its FIN, and then took whatever the
peer went on sending: it threw the data away, acknowledged it and opened its window wide. A server
whose download the app had stopped reading kept sending, so the data came at full speed for as
long as the server had any. Through a WireGuard endpoint over loopback that was 1.2 Gbit/s for
half a minute after each download that was closed, and every other connection through the tunnel
was 3 to 9 ms late behind it: in about one test in four the round trip was 3 to 9 ms instead of
0.2, the upload ran at half its speed and the CPU used doubled. A connection that was reset after
its FIN was lost answered every packet with a reset at a sequence number the peer does not take,
and the peer every reset with an acknowledgement, for a second.

**Fix:** a connection the app closed is reset when new data arrives, as RFC 1122 asks and Linux
and gVisor do, and the reset that answers a segment takes the sequence number the segment
acknowledges (RFC 793), which the peer takes. `TestH_GoClosedConnectionResetsAPeerThatKeepsSending`
and `TestH_GoResetTakesTheAcknowledgedSequence` (sing-tun) fail without it.

## WireGuard: MTU discovery lowered the MTU at random and closed the connections

Commit: `f42360238`

**What happened:** MTU discovery sent an ICMP echo request of every size from 576 to the MTU, in
steps of 16, all at once, and took the largest size answered as the MTU. The target and the
routers on the way answer only so many requests a second, and a busy tunnel drops packets: of a
burst of fifty some were always lost. On a path that carries 1420, every start found an MTU
between 1120 and 1408, and closed the TCP connections made through the endpoint, as discovery does
when the MTU is lowered: a download that had begun broke. When the path stopped answering during
the search, the MTU became 576.

**Fix:** the configured MTU is tried first, and a binary search runs only when it does not get
through. Each request goes out with one of the smallest size, and a size counts as too large only
when it is lost three times while the small one is answered; a try in which neither is answered
tells nothing. A path that stops answering leaves the MTU as it is. `TestSearchLimitedAnswers` and
`TestSearchNoAnswer` (`hiddify/mtusearch`) fail without it.

## Paced reads: QUIC, OpenVPN and yamux downloads ran slower on short paths

Commit: `a20810aa5` and `fdd816570` (wireguard-go fork `32f4b53`)

**What happened:**

- A busy datagram socket waited up to 1 ms after each wake-up before it read, whatever its path.
  On loopback, the local network or to a server nearby that is several round trips: QUIC's
  congestion control saw every acknowledgement late and slowed down. Over loopback a Hysteria2
  download ran at a third of its speed, TrustTunnel over QUIC and XHTTP over HTTP/3 at less than
  half, uploads through TUIC and OpenVPN over UDP lost 10 to 30%, and OpenVPN's round trip was
  0.31 ms instead of 0.18.
- A TCP connection faster than 4 MB a second waited at least 250 microseconds before each read of
  an emptied socket. A stream behind a multiplexer's window stops when the window is full, and a
  yamux download through one stream ran at 4 Gbit/s instead of 11: the trial that watched the
  first windows of pacing had passed while the reader was still the slower side.
- WireGuard paced the acknowledgements of an upload as well, which cost it 13% of its speed.

**Fix:** the wait of a datagram socket read through its raw connection is at most a 32nd of its
path's round trip, which it measures with its first exchange, and there is none while the round
trip is not known or the peer is this machine. A paced TCP connection is tried without the waits
after 0.2 seconds, then at growing intervals, and whenever it slows down: if it is 15% faster
then, it is left alone. A connection that sends more than it receives is not paced, and neither
is a WireGuard tunnel that sends as many datagrams as it receives. `TestH_WakePaceNeedsALongPath`,
`TestH_ReadPaceFindsASenderBehindAWindow`, `TestH_ReadPaceLeavesAnUploadAlone` and
`TestH_ReceivePaceLeavesAnUploadAlone` (wireguard-go) fail without it.

## XHTTP over REALITY: every proxy connection made a handshake of its own

Commit: `74d48e631`

**What happened:** the client chose the HTTP version from the TLS ALPN, and REALITY has none: it

## XHTTP: in packet-up the first bytes of every connection left 30 ms late

Commit: `fab182535`

**What happened:** VLESS, VMess and Trojan write their request as soon as a connection is up, and

## WARP: with keep top, a device could not register through the resting proxies

Commit: `40b35d1ff`

**What happened:** when WARP cannot register its device over its own detour, it tries every
outbound until one reaches the WARP API. With keep top most of the profile's proxies rest: lazy and
closed, and put back to rest, which closes them under a dial under way, whenever the pick changes.
The registration went through the outbounds in config order, untested and dead ones first, and a
pick could cut the one attempt that would have worked: the device stayed unregistered and the hop
logged `register WARP masque device: context canceled` (hiddify-app#2566, Android).

**Fix:** the fallback tries the outbounds that answer their ping first, fastest first (the last
good ping of one that rests counts), then the others as before, and holds each lazy one awake for

to rest after, as any idle lazy outbound (`protocol/warp/h_register_detours.go`).

## XHTTP: connections to the server stayed open after they were no longer needed

Commit: `511c5cf72`

**What happened:**

- Closing an XHTTP outbound closed none of its connections to the server, and neither did a change
  of network. An HTTP/2 connection stayed for five idle minutes. An HTTP/3 connection kept itself
  alive with a packet every 10 seconds until `h_max_reusable_secs` was over, up to 50 minutes, and
  its UDP socket stayed open even after that, as quic-go does not close a socket it was given.
  With `max_concurrency` 1, the default, there is one such connection for every proxy connection
  that was open at the same time, and keep top closes each lazy outbound after its test: a test of
  a profile with many XHTTP outbounds left tens of connections sending keepalives.
- A TLS handshake that failed left its TCP connection open. The router tracks the connections of
  a dialer, so it stayed for good: one for every test of a server whose certificate is not
  accepted.
- When a connection's upload requests were used up (`h_max_request_times`) and its uploads moved
  to another HTTP connection, the first one stayed counted as in use for good and the last one was
  released without having been taken, so that two proxy connections could share it.
- A download that the application stopped was logged as an error over HTTP/3
  (`H3_REQUEST_CANCELLED (local)`).

**Fix:** closing the transport closes its connections, HTTP/3 ones with their sockets, and the
transport can be used again, as after a change of network. An HTTP connection with nothing on it
is closed after one minute, and the one used last after five. A failed handshake closes its
connection, and the socket of an HTTP/3 connection is closed when the connection ends. The uploads
that move to another HTTP connection take and release it themselves. The errors an HTTP/3 stream
ends with when it is closed are known as a closed connection, as HTTP/2's are. Tests cover each
of these for HTTP/1.1, HTTP/2 and HTTP/3; they fail without the fix.

**What happened:** After the pick, keep top looked at the outbounds at rest again only when every

## UDP: an idle session lived up to twice its udp_timeout

Commit: `95d342987` (sing fork `b40ea07`)

**What happened:** An inbound's `udp_timeout` (SOCKS, mixed and others) ends a UDP session that has
been idle that long. Each read waited one timeout from the moment it started. A reply sent back to
the client while the read waited counted as activity, so when the deadline came the session was not
idle yet, and the next deadline was a whole timeout away again. An idle session could live up to
twice its timeout, holding its socket and NAT entry that much longer.

**Fix:** The deadline is one timeout after the last packet in either direction.

## XHTTP with multiplex: every connection was reset, and a stalled TLS handshake crashed the core

Commit: `166104c63`

**What happened:** a VLESS outbound with an XHTTP transport and `multiplex` on (yamux, smux or

## IPv6 by outbound: IPv6-first sites still died through a proxy without IPv6

Commit: `d992de248`

**What happened:** The IPv6 probe that 5.4.0 added opened a connection to a public resolver's
IPv6 address through the outbound and took an open connection as IPv6 carried. A VLESS, Trojan,
VMess or Shadowsocks dial returns before the proxy's server has connected anywhere, so the probe
said yes for every such proxy, AAAA answers went out, Chrome, Samsung Internet and the YouTube
app reached Google over IPv6, the proxy closed the connection and the page showed
`ERR_CONNECTION_CLOSED`, while Telegram and Instagram, on IPv4, worked (hiddify-app 5.3 and 5.4 on
Android 16 and 17, #2420). The probe was also traffic of its own to Google and Cloudflare

mode turns it on. See [IPv6 by outbound](../features/dns/ipv6-by-outbound.en.md).

## Monitoring: the selected proxy's ping arrived late

Commit: `f7d6695cb`

**What happened:** The first test cycle took the members fastest-first by last run's result,

## Monitoring: after a while nothing was tested any more

Commit: `f7d6695cb`

**What happened:** A URL test dials the outbound with a deadline in its context. An outbound
whose dial ignores that deadline, as a dial into a native library may (cronet's naive dial, by
the logs), never returned, so its worker waited for good, and so did the cycle waiting for that
result. A few such tests, and every worker was held: no cycle, no priority test, no ping for

**Fix:** A worker waits for one test at most twice its deadline plus `url_test_timeout` and

## Security: every inbound listened on MPTCP

Commit: `9aca6c8c1`

**What happened:** Go 1.24 and newer listen on Multipath TCP by default on Linux, and the Linux
kernel let a remote root listen on IPv4 MPTCP. The TCP listener and the dialer set MPTCP only

## Balancer: every test round moved the selection and cut every connection

Commit: `d23f1250b`

**What happened:** The `lowest-delay` strategy took the new minimum at every monitoring
update, with no tolerance (the option was accepted and ignored), and the balancer then closed
every connection through it, inbound ones included with `interrupt_exist_connections`. Two
servers with close delays swapped at every round, and during a ping of all servers the results

## XHTTP: the server leaked goroutines and connections

Commit: `0f0f6966e`

**What happened:** On an XHTTP inbound, the download (GET) request hands its connection to the

## HTTP transport (HTTP/1.1): Trojan behind Xray's raw HTTP header answered 400

Commit: `e29388e76`

**What happened:** A Trojan outbound with the `http` transport over HTTP/1.1 (Xray's "raw TCP with HTTP

Psiphon controller only dials while a tunnel is up, and its "no active tunnels" error marks it as
not connected.

## WARP scanner: probes did not send what the device sends

Commit: `28ff47e9b`

**What happened:** The scanner judges an endpoint by a handshake made after the same noise the
device sends. But in the default noise mode the probe left out the short header the device puts
before each fake packet, and with `awg` it sent the WireGuard `noise` instead of the AmneziaWG
junk and special packets. An endpoint could then answer the probe and not the device, or the
other way round.

**Fix:** The device and the probe build the fake packets with the same code, and with `awg` the
probe sends `i1`–`i5` and the `jc` junk packets. Tested with every noise preset against Cloudflare.

## Shadowsocks: QUIC protocols never connected through it

Commit: `1e2ddd7fd`

**What happened:** Hysteria2, and any other QUIC protocol, through a Shadowsocks detour never
connected. QUIC reads each packet into a buffer of about one packet, the Shadowsocks client
decrypts in place in that buffer, and a full packet with its salt and tag did not fit. It failed
with "cipher: message authentication failed", and the QUIC connection ended.

**Fix:** The Shadowsocks client reads each packet whole and copies it. Tested with Hysteria2
through Shadowsocks, VLESS and Trojan; only Shadowsocks failed before.

## WARP: background work outlived the box, and AmneziaWG through a cold detour never started

Commit: `79d187b08`

**What happened:** The box closes each endpoint's scope, not the endpoint, so WARP's port
rotation, failover and their goroutines kept running after the box closed, and tried to start
replacements that failed with "context canceled". Separately, AmneziaWG opens its socket when it
starts, and fails when the detour does not work yet (a group still on a dead member); WARP then
gave up and stayed "endpoint not initialized" for good, even after the detour recovered.

**Fix:** WARP's background work stops when its scope closes. The first start of the tunnel is
retried with a backoff (1 s, doubling, up to 30 s), like the registration. Tested live through a
selector that moves from a dead member to a working one, and with a unit test that fails without
the fix.

## MASQUE: a tunnel set up while the outbound closed stayed open

Commit: `ff42383d6`

**What happened:** Closing a `masque` outbound whose tunnel was still being set up returned

**Fix:** Close ends a registration in progress, and a tunnel set up meanwhile is closed when its

## masque-client: shown as connected before it reached the server

**What happened:** The upstream `masque-client` endpoint used the default ready state, so it
showed as connected while it had no session with the server.

**Fix:** It is ready only while a session with the server is up. An `on_demand` endpoint, which

## Psiphon: connected state raced, and a notice could crash the process

Commit: `7a85e7be9`

**What happened:** The connected flag was written from a new goroutine for each notice and read
without a lock. It was only ever set, never cleared when the tunnel count dropped to zero. A

**Fix:** Notices are handled in order, the state is atomic and follows the tunnel count, and a

## Monitoring: a selection reached the app late, and chained outbounds were tested too early

Commit: `af68dde0a`

**What happened:** A selection change waited for the debounce meant for bursts of test results
before the group's subscribers saw it, and a subscriber busy with the last update could miss it.
An outbound behind a group detour was tested before any member of that group worked, so a

**Fix:** A selection is published at once, to the group, its parents and the catch-all group,

## Sudoku: a large transfer to a slow reader reset the stream

Commit: `16096efa2`

**What happened:** The Sudoku mux had no flow control. Once a stream held 4 MiB its reader had not
read, the next frame reset the stream with "mux receive queue full". The mux's own test failed in

## MASQUE: HTTP/3 never connected through Shadowsocks, VLESS or Trojan

Commit: `1f44631b9`

**What happened:** WARP over MASQUE with HTTP/3 worked through a SOCKS detour only. QUIC reads each

## Psiphon: every binary crashed at start when built with Go 1.27

## Shadowsocks simple-obfs: obfs_host was not checked

**What happened:** The Shadowsocks inbound accepted `obfs_host` but never compared it with the host

## DNS: bypass_if_failed ignored an empty answer in legacy mode

Commit: `0e67074d9`

**What happened:** In legacy DNS mode, a rule with `bypass_if_failed` moved on to the next rule

## WARP: WireGuard through a detour often never connected

Commit: `ce64e6017`

**What happened:** WARP over WireGuard behind a detour (for example Extra Security) often never
connected. WireGuard sent the handshake to the profile's IPv4 and IPv6 addresses through one UDP

answer was also used for good. WARP and MASQUE showed as connected as soon as they were set up,

server. Tested live through a working and a dead detour, for WireGuard, AmneziaWG, and MASQUE over
HTTP/3 and HTTP/2.

## Call: route rules stopped after a reconnect, and a failed connect was final

Commit: `3f48fb169`

**What happened:** On `vk`, `telemost` and `dion`, after the call reconnected, the server side

## SSH inbound: host_key_algorithms, network and deadlines were ignored

Commit: `0ebdf81b7`

**What happened:** The SSH inbound read `host_key_algorithms` and `network` but used neither.

## Reports: archives held sensitive data

Commit: `37d5006d1`

**What happened:** Report archives are not encrypted, but when the app asked for encryption they

## XHTTP: auto mode did not match Xray's client

Commit: `0493e3f8d`

**What happened:** Four pieces of XHTTP state were shared between goroutines without
synchronization: the download stream's reader, a buffer's length read after it was handed off,
the upload queue's closed flag and reader, and the connection addresses. Under load these could
corrupt data or crash the process.

**Fix:** Each is now guarded or passed atomically.

## gVisor: a failed TCP handshake could crash the process

Commit: `31947f874` (gVisor fork `d811af3`)

**What happened:** In the gVisor network stack, a TCP segment that arrived just after a handshake
failed, while the connection was being closed, used state that had already been cleared. The whole
process crashed. The gVisor TUN stack and the MASQUE and AmneziaWG endpoints use this stack.

**Fix:** Such a segment is ignored, and closing the connection cleans up. gVisor is now forked
under `replace/gvisor`.

## TUN: new TCP connections refused after a listener error

Commit: `de0aae2c2` (sing-tun fork `abfac68`)

**What happened:** The system TUN stack hands each new TCP connection to a local listener. Any
error while accepting, even a short-lived one such as running out of file descriptors, stopped the
listener's loop for good. Every new TCP connection was then refused until the VPN restarted, while
UDP kept working.

**Fix:** Short-lived errors are waited out, and a listener that died is recreated. sing-tun is now
forked under `replace/sing-tun`.

## WireGuard: recovery after the network goes bad

Commits: `386158d33` and `31c0f5732` (wireguard-go fork `f191d67`, `b46c414`, `a7a59c8`, `6f870fd`,
`5e21bd6`, `a6fcdc9`)

**What happened:**

- After the device slept, or when DPI flagged a connection, handshakes kept failing from the same
  source port, and WireGuard and WARP did not recover until the network changed.
- A receive routine that met a lasting socket error stopped, and nothing restarted it.
- WireGuard did not start at all on a host or interface without IPv6.
- Noise (fake) packets: only the first one was sent, the start of each was cut off, and the top of
  every configured range (count, size and delay) was never used.

**Fix:**

- After failed handshakes, the socket is reopened on a new port. This happens once the handshake
  cycle gives up, or after 3 unanswered attempts when the session is already dead, at most once
  every 90 seconds. A configured `listen_port` is kept.
- A receive routine that stops reopens the socket.
- IPv4 is kept when IPv6 cannot be opened.
- All noise packets are sent whole, and ranges include their upper bound.

## Local DNS on Linux: no fallback when systemd-resolved is incompatible

Commit: `53aa823c9`

**What happened:** On Linux, the `local` DNS server failed outright when the systemd-resolved
service lacked a method it needs.

**Fix:** It falls back to `/etc/resolv.conf`, and returns to systemd-resolved once it works.

## MASQUE: no fallback from HTTP/3 when UDP is blocked

Commit: `787f27a51`

**What happened:** When UDP was blocked, the HTTP/3 attempt used up the whole connection timeout,
so there was no time left to fall back to HTTP/2. A session that failed on HTTP/3 also kept retrying
HTTP/3.

**Fix:** The HTTP/3 attempt gets at most 5 seconds (or half the time left), and a failed HTTP/3
session makes the next attempt fall back.

## Tailscale: control connection over port 80

Commit: `a210bd114`

**What happened:** Tailscale's control connection first tried a plaintext HTTP upgrade on port 80,
which filtered networks intercept or recognize, and moved to port 443 only after a delay.

**Fix:** It goes straight to port 443. Set `TS_FORCE_NOISE_443=false` to restore the old behavior.

## Crash reports: unbounded, and they carried the configuration

Commit: `1017225d5`

**What happened:** Every crash added a report that was never removed. Each report also carried a
copy of the configuration, including server addresses, keys and passwords, although reports are
made to be shared.

**Fix:** The newest 32 reports of each kind are kept, up to 64 MiB. Reports no longer include the
configuration, and an old copy is removed.

## SOCKS: UDP never reached servers that answer with 0.0.0.0

Commit: `70d6601fd`

**What happened:** Many SOCKS5 servers answer a UDP request with the address `0.0.0.0`, meaning
"the address you reached me on". sing-box sent UDP to that address, which is the local machine.

**Fix:** It sends UDP to the server's address instead.

## WireGuard: packets larger than the path were dropped

Commit: `1ed324a7b`

**What happened:** sing-box marks outgoing UDP as "do not fragment". A WireGuard packet larger than
the network path allows, as in a tunnel inside another tunnel, was dropped, and large transfers
stalled.

**Fix:** The system may fragment WireGuard packets, as official WireGuard allows. `udp_fragment`
still overrides it.

## WireGuard: a stuck detour froze the tunnel

Commits: `304bde1fd`, `dd032dfd7`

**What happened:** WireGuard's connection through a `detour` was dialed while holding the lock that
sending and receiving wait on, with no time limit. A detour that hung froze the whole tunnel. The
same code also had a data race.

**Fix:** That dial gives up after 15 seconds and is retried, and the race is fixed.

## WireGuard, AmneziaWG, MASQUE: slow failure for unreachable hosts

Commit: `b1d063442`

**What happened:** A TCP connection through these tunnels to a host that never answers waited one
to two minutes before failing, against 15 seconds for a direct connection.

**Fix:** It fails after 15 seconds.

## Clash API: FakeIP flush did nothing

Commit: `3949d2479`

**What happened:** The Clash API's FakeIP flush cleared only the cache file. With the default
settings, FakeIP mappings live in memory, so nothing was cleared.

**Fix:** The flush clears the FakeIP store in use and restarts address allocation.

## HTTP transport: client cancellations logged as errors

Commit: `0ac410ae9`

**What happened:** On the server side of the HTTP transport, a client that cancelled its stream was
logged as a failure.

**Fix:** It is treated as a closed connection.

## Shadowsocks 2022: "bad request salt"

Commit: `fb981ebba`

**What happened:** With Shadowsocks 2022, a reply could be read before the first upload finished.
The connection then failed with "bad request salt", most often when the first upload was large.

**Fix:** The request header is written while connecting, before the connection is used.

## Cache file: entries lost when saving failed

Commit: `6927625a1`

**What happened:** When the cache file could not be written (a full disk, a read-only file), the
pending DNS cache and FakeIP entries were dropped from memory as well.

**Fix:** They are kept and saved at the next attempt.

## DNS: duplicate queries after a failure

Commit: `42acc7903`

**What happened:** Identical DNS queries wait for the one already sent. When that query failed,
every waiting query went to the server separately.

**Fix:** The waiting queries share one new query.

## DNS outbound: connections never closed

Commit: `dfb54ab49`

**What happened:** A DNS session through the `dns` outbound never reported that it ended. The
connection stayed in the connection list and statistics, and some inbounds waited for it until
shutdown.

**Fix:** The end of the session is reported.

## Routing: UDP sessions leaked after a routing error

Commit: `7ea28f847`

**What happened:** When a UDP session from Shadowsocks, multiplex or UDP-over-TCP could not be
routed, the code handling it waited until shutdown.

**Fix:** It returns after the error.

## Startup held by a slow multiplex connection

Commit: `0cb109659`

**What happened:** Starting the service could wait up to 15 seconds for a multiplexed connection
being opened through a slow or dead server.

**Fix:** That work happens after startup.

## XHTTP: deadlines silently ignored

Commits: `6534ce882`, `1288cc7c6`

**What happened:** XHTTP connections accepted time limits and ignored them, so a wait on a silent
peer never ended. Closing a connection also lost the download side's error.

**Fix:** XHTTP connections report that they need help with time limits, and the router adds it,
as for gRPC and HTTP. The error is returned.

## VLESS encryption: hang on a silent server

Commit: `3db8eb988`

**What happened:** With VLESS encryption, a server that accepted the connection and never answered
held the connection, and any URL test through it, forever.

**Fix:** The handshake stops when its time limit ends.

## URL test: tests kept running after a reload

Commit: `6360e3afb`

**What happened:** After a configuration reload, the old URL test group's tests kept running for up
to 15 seconds and wrote results for outbounds that might no longer exist.

**Fix:** Closing the group stops its tests.

## TUN: DNS stalled the whole tunnel

Commit: `d098fded1`

**What happened:** DNS queries caught by the TUN were handled on the tunnel's packet loop. With a
DNS server behind a dead proxy, each query held every packet of the tunnel for 10 seconds.

**Fix:** Each query is handled separately, at most 256 at once.

## libbox: Connections was not safe for concurrent use

Commit: `767a337ef`

**What happened:** A platform app applies connection events on its command client's thread, and
its UI filters, sorts and lists the same `Connections` object on the main thread. Nothing guarded
the map and slices they share, so the connection list could crash the app or show broken entries.

**Fix:** Every exported method of `Connections` now takes a lock.

## Balancer: sticky sessions landed on dead members

Commit: `299f7c824`

**What happened:** When the member remembered for a session was dead, `sticky-sessions` picked
again with a seed that was often identical on every retry. After the last retry it used the pick
without checking it, so about half of the new sessions went to a dead member.

**Fix:** Each retry draws with a new seed. If no retry finds a live member, the first live member
is used. A dead member is used only when none is alive.

## Balancer: untested members counted as the fastest ones

Commit: `26038512b`

**What happened:** `consistent-hashing` and `sticky-sessions` read the raw test delay. A member that
was never tested has a delay of 0, so it looked like the fastest member and got traffic. A delay
restored from the cache was trusted as if it were fresh.

**Fix:** These strategies now use the same adjusted delay as `lowest-delay` and `round-robin`. An
untested member counts as timed out, and a cached delay gets a penalty.

## Balancer: a large delay ratio overflowed

Commit: `9352492aa`

**What happened:** The largest acceptable delay is the smallest delay × `delay_acceptable_ratio`.
It was stored in a 16-bit number, which wraps past 65,535 ms. A cached delay gets a 20,000 ms
penalty, so with a ratio of 3 two cached members gave a limit of about 9,000 ms, and `round-robin`
then used only one of them.

**Fix:** The limit is computed in one place and capped just below the timeout delay. A timed-out
member is still never accepted.

## Balancer: round-robin reported no selected member

Commit: `c4c581f38`

**What happened:** A `round-robin` balancer always reported an empty current member, so the app and
the Clash API showed nothing selected.

**Fix:** It reports the member the next TCP connection goes to.

## Balancer: closing did not stop the worker

Commit: `e3a6b22fa`

**What happened:** `Close` did nothing, so the worker that follows URL-test results kept running
until the whole service stopped. After a configuration reload, the old balancer kept updating
itself.

**Fix:** `Close` stops the worker.

## SSH: no background connection after start

Commit: `69fa3a66e`

**What happened:** The SSH outbound connects in the background after start and reconnects when the
connection drops, so it is ready and tested before any traffic. After the move to sing-box v1.15's
startup stages, this step was never run. The outbound stayed not ready, and the URL test skipped
it, until traffic arrived.

**Fix:** The background connection starts again once the service has started.

## Startup: some outbounds were never started, and the balancer crashed

Commit: `ac35f63e4`

**What happened:** sing-box v1.15 starts components in stages. Outbounds written for the older
startup (`balancer`, `psiphon`, `dnstt` and `gooserelay`) were only closed at shutdown and never
started. A balancer that was never started has no strategy, and its first connection crashed the
whole process.

**Fix:** These outbounds go through the startup stages again: preparation, start, and the step
after the service has started.

## WARP: an incomplete profile crashed the process

Commit: `35779caa3`

**What happened:** The WARP endpoint starts in the background, so any crash there takes the whole
process down. Three cases crashed it:

- the profile request failed and there was no outbound to retry through;
- the profile (cached, written in the config, or from the API) had no peers or no ports;
- the profile had no interface addresses.

**Fix:** Each case now reports an error. The peer address and port are picked with checks, in this
order: the configured `server` and `server_port`, a port listed in the profile, or the port in the
host name. A missing address family is skipped.

## TUIC: a misspelled UDP relay mode was accepted

Commit: `36861907a`

**What happened:** Any `udp_relay_mode` other than `quic`, such as `quick` or `Native`, silently
meant `native`.

**Fix:** An empty value or `native` means native, and `quic` means QUIC. Any other value fails
when the configuration loads.

## XHTTP: lost dial errors and accepted rejected uploads

Commit: `fee26e298`

**What happened:**

- When the download stream could not connect, the error was lost. The caller got a reader that
  never returned data, so the connection hung until it timed out.
- On HTTP/2 and HTTP/3, an upload the server rejected (any status other than 200) counted as sent.
- The closed flag was read and written from different goroutines without synchronization.

**Fix:** The dial error reaches the caller. On HTTP/2 and HTTP/3, a status other than 200 is an
error, as in Xray. The closed flag is atomic.

## REALITY: a long short_id crashed the process

Commit: `f6f378e81`

**What happened:** A REALITY `short_id` is at most 8 bytes, which is 16 hex digits. A longer value
overflowed the buffer it was decoded into and crashed the process, on both the client and the
server.

**Fix:** A `short_id` longer than 16 hex digits is a configuration error.

## VLESS: a failed handshake leaked the connection

Commit: `ea3c70fa5`

**What happened:** When the TLS handshake or the VLESS encryption handshake failed, the underlying
TCP connection was never closed. A failed encryption handshake also replaced the connection with an
empty value, which could crash later code. This applied to both TCP and UDP.

**Fix:** The original connection is closed on any handshake failure, and it is replaced only after
a successful handshake.

## Trojan: a disabled TLS block crashed the process

Commit: `27c97f0d8`

**What happened:** A Trojan outbound with a `tls` block where `enabled` is `false` built a TLS dialer
with no TLS settings, and the first connection crashed the process.

**Fix:** The TLS dialer is built only when TLS is enabled.
