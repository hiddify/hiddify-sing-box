# پردازنده‌های تطبیقی (Adaptive processors)

[English](adaptive-processors.en.md) · [همهٔ قابلیت‌های هیدیفای](../index.fa.md)

با `experimental.debug.procs`، تعداد پردازنده‌هایی که runtime زبان Go به کار می‌برد (GOMAXPROCS)
از بار پیروی می‌کند: تا وقتی پراکسی کار کمی دارد یکی، و وقتی پرکار است بیشتر. بدون آن، runtime
همیشه برای هر هستهٔ CPU یک پردازنده به کار می‌برد.

## چرا از آن استفاده کنیم

مسیر داده در پراکسی زنجیره‌ای از goroutineهاست که هر بسته را به بعدی می‌دهند: خوانندهٔ سوکت، اتصال
QUIC یا WireGuard، خوانندهٔ stream و نویسندهٔ تأییدها (ACK). وقتی پردازندهٔ بی‌کار هست، runtime برای
هر یک از این دست‌به‌دست‌شدن‌ها یک thread دیگر را بیدار می‌کند. آن thread می‌بیند کار قبلاً برداشته
شده، لحظه‌ای دنبال کار دیگر می‌گردد و دوباره می‌خوابد. در تونلی که هر ثانیه هزاران بسته می‌برد،
همین بیدارشدن‌ها بیشترِ CPU مصرفی پراکسی است، بیش از رمزنگاری و فراخوانی‌های سیستمی روی هم.

با یک پردازنده، goroutineی که بسته‌ای به آن داده می‌شود به‌سادگی روی همان threadی که بیدار است
اجرا می‌شود. همان دانلود با همان سرعت حدود نصف CPU می‌گیرد. اندازه‌گیری در macOS (تراشهٔ اپل، ۱۲
هسته)، ثانیهٔ CPU برای هر گیگابایت دانلود:

| پروتکل | همهٔ هسته‌ها | تطبیقی |
|---|---|---|
| Hysteria2 (salamander) | 13.3 | 5.3 |
| Hysteria | 15.3 | 5.5 |
| TUIC | 8.7 | 3.6 |
| XHTTP روی HTTP/3 | 12.0 | 7.5 |
| WireGuard | 13.3 | 9.2 |
| OpenVPN روی UDP | 7.7 | 4.5 |
| OpenVPN روی TCP | 6.7 | 3.9 |
| gRPC | 4.0 | 2.2 |
| XHTTP روی HTTP/1.1 | 2.7 | 1.6 |
| Shadowsocks 2022 | 2.3 | 1.5 |

آپلودها هم تقریباً همین‌قدر سود می‌برند. در لینوکس بیدارکردن thread هزینهٔ کمتری دارد و سود کمتر
است: روی یک سرور ۱۲ هسته‌ای مشترک، Hysteria2 یک‌چهارم تا یک‌سوم CPU کمتری گرفت، TUIC تا یک‌چهارم
کمتر، و پروتکل‌های TCP مثل قبل.

## چطور از فیلترینگ عبور می‌کند

عبور نمی‌دهد. فقط مقدار CPU مصرفی پراکسی را تغییر می‌دهد.

## چطور کار می‌کند

- تنظیم‌کننده پس از شروع box شروع می‌شود، پس هر چیزی که در شروع خود را با تعداد پردازنده‌ها اندازه
  می‌کند هنوز همهٔ آن‌ها را می‌بیند. سپس تعداد را روی `min` می‌گذارد.
- هر ۱۰۰ میلی‌ثانیه می‌خواند که goroutineها چقدر منتظر پردازنده مانده‌اند؛ این را خود runtime
  اندازه می‌گیرد. جمع انتظارهای آن بازه تقسیم بر طول بازه، تعداد goroutineهایی است که به‌طور
  میانگین منتظر بوده‌اند: همان بار، مانند load average سیستم.
- بار ۱ یا بیشتر یعنی کار بیش از توان پردازنده‌هاست: یک پردازنده اضافه می‌کند، و اگر بار ۴ یا بیشتر
  باشد دو تا. شروع برنامه، تست صدها پراکسی یا دانلود چند گیگابیت بر ثانیه، در یک یا دو بازه
  هسته‌هایش را می‌گیرد.
- پس از ۳ ثانیهٔ آرام (بار کمتر از ۰٫۲۵) یک پردازنده را برمی‌دارد و یک ثانیه نگاه می‌کند. اگر بار
  برگشت، پردازنده را پس می‌دهد و پیش از تلاش بعدی دو برابر صبر می‌کند، تا ۲ دقیقه.
- وقتی هیچ چیزی اجرا نمی‌شود کمتر نگاه می‌کند، تا هر ۲ ثانیه یک بار، تا پراکسی بی‌کار برای این کار
  بیدار نشود.
- وقتی box بسته می‌شود، runtime همان تعدادی را که داشت پس می‌گیرد.
- GOMAXPROCS مال کل پروسه است، پس هر بار فقط یک تنظیم‌کننده اجرا می‌شود. روی این پردازنده‌ها فقط
  کد Go اجرا می‌شود: برنامه‌ای که با هسته در یک پروسه است تأثیری نمی‌گیرد.

## پیکربندی

```json
{
  "experimental": {
    "debug": {
      "procs": {
        "enabled": true
      }
    }
  }
}
```

| فیلد | نوع | پیش‌فرض | معنی |
|---|---|---|---|
| `procs.enabled` | bool | `false` | تعداد پردازنده‌های Go از بار پیروی کند. |
| `procs.min` | int | `1` | کمترین تعداد پردازنده. |
| `procs.max` | int | هسته‌های CPU | بیشترین تعداد. |

`max` کمتر از `min` یا عدد منفی، هنگام بارگذاری پیکربندی خطای پیکربندی است.

### نکته‌ها

- hiddify-core آن را در پیکربندی‌هایی که می‌سازد روشن می‌کند.
- `GOMAXPROCS` در محیط (environment) عددی است که کسی انتخاب کرده: تنظیم‌کننده شروع نمی‌شود.
  `HIDDIFY_PROCS=off` در محیط آن را خاموش می‌کند، پیکربندی هر چه بگوید، و `HIDDIFY_PROCS=auto`
  روشنش می‌کند، برای مقایسه.
- یک پردازنده بهایی دارد. garbage collector سهم خود از آن پردازنده را تکه‌تکه می‌گیرد، پس هنگام
  دانلود سنگین ممکن است یک goroutine چند بار در ثانیه چند میلی‌ثانیه منتظر بماند؛ و فراخوانی سیستمی
  که بلوکه می‌شود، مانند sync فایل cache روی دیسک، پردازنده را نگه می‌دارد تا runtime آن را به دیگری
  بدهد، که تا ۲۰ میلی‌ثانیه طول می‌کشد. هیچ‌کدام بار حساب نمی‌شوند. اگر این در تماس‌ها یا بازی‌ها دیده
  شد، `min` را ۲ بگذارید: هر دو را برطرف می‌کند و حدود نصف صرفه‌جویی را نگه می‌دارد.
- روی دستگاهی که با کارهای دیگر مشغول است، threadهای پراکسی هم منتظر سیستم می‌مانند و تنظیم‌کننده
  پردازنده اضافه می‌کند: این رفتار عمدی است.
- در لاگ هنگام شروع `procs: 1 Go processor(s) while there is little to do, up to 12 under load`
  می‌آید، و هر تغییر در سطح debug.
